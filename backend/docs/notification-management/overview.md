## 1. Overview

The Nexora Notification Management module provides a centralized system for informing users about important activities occurring within the platform.

The current notification system supports events generated by:

- Connection requests.
- Connection acceptance.
- Connection rejection.
- Messages from connected users.

Notifications are persisted in MongoDB so that notification history remains available even when a user is not currently connected to the application.

The system uses HTTP APIs for persistent notification operations and Socket.IO for real-time synchronization with connected frontend clients.

The architecture therefore separates:

- Persistent notification data.
- Notification business operations.
- Real-time client synchronization.
- Frontend notification presentation.

Connection Management and Message Management remain responsible for their own business operations and invoke the Notification Service when a notification-generating event occurs.

---

## 2. Objectives

The Notification Management module is designed to:

- Inform users about relevant platform activities.
- Maintain persistent notification history.
- Track notification read state.
- Provide unread notification counts.
- Allow individual notifications to be marked as read.
- Allow all notifications to be marked as read.
- Associate notifications with relevant application entities.
- Centralize notification creation through a reusable service.
- Enforce authenticated user ownership.
- Support paginated notification retrieval.
- Synchronize relevant notification state with connected clients through Socket.IO.

---

## 3. Core Architecture

The Notification Management module follows the Nexora layered backend architecture:

```text
Client
   ↓
Route
   ↓
Authentication Middleware
   ↓
Controller
   ↓
Service
   ↓
Model
   ↓
MongoDB
```

Notification creation is initiated by other business modules:

```text
Connection Service ──┐
                     ├──> createNotification()
Message Service ─────┘
                           ↓
                    Notification Service
                           ↓
                    Notification Model
                           ↓
                        MongoDB
```

The Notification Controller handles HTTP-level operations such as:

- Retrieving notifications.
- Retrieving unread counts.
- Marking one notification as read.
- Marking all notifications as read.

The Notification Service contains notification-specific business logic.

The Notification Model defines the persistent notification data.

Connection Management and Message Management call `createNotification()` when their business events require a notification.

Socket.IO operates as a separate real-time synchronization layer and does not replace MongoDB persistence.

---

## 4. Notification Types

The current implementation supports the following notification types:

| Type | Trigger |
|---|---|
| `connection_request` | A user sends a connection request |
| `connection_accepted` | A connection request is accepted |
| `connection_rejected` | A connection request is rejected |
| `message` | A connected user sends a message |

Connection-related notifications are generated by Connection Management.

Message-related notifications are generated by Message Management.

The notification type is stored as an enumerated value in the Notification model.

---

## 5. Notification Lifecycle

A notification follows the general lifecycle below:

```text
User Action
    ↓
Business Service
    ↓
createNotification()
    ↓
Notification Document
    ↓
MongoDB Persistence
    ↓
Unread
    ↓
Read
```

The relevant business service creates the notification when the associated event occurs.

The Notification Service persists the notification in MongoDB.

The notification can then be retrieved through the HTTP notification API.

When the user is connected to the application, relevant state can additionally be synchronized through Socket.IO.

A notification remains stored in MongoDB after it has been read.

## 6. Connection Management Integration

Notification Management is integrated with Connection Management.

When a user sends a connection request:

```text
User A
   ↓
Connection Service
   ↓
Connection Created
   ↓
createNotification()
   ↓
User B receives connection_request
```

When a pending connection request is automatically accepted because the recipient sends a reciprocal request, the original requester receives a `connection_accepted` notification.

Connection-related notification creation is handled through:

```text
src/services/connection.service.js
```

The Connection Service remains responsible for connection business rules.

The Notification Service remains responsible for notification creation and notification data handling.

Connection notifications are persisted in MongoDB and retrieved through the notification API.

---

## 7. Message Management Integration

Notification Management is also integrated with Message Management.

When a connected user sends a message:

```text
Message Service
      │
      ├── Message created
      │
      ├── Conversation updated
      │
      └── createNotification()
                ↓
        Notification persisted
```

Message notifications contain references to the relevant messaging context, including:

- Conversation.
- Message.
- Sender.
- Recipient.

Message-related notification creation is handled through:

```text
src/services/message.service.js
```

The Message Service remains responsible for message and conversation business logic.

The Notification Service remains responsible for notification creation.

Message-related notification state can also participate in Socket.IO synchronization for connected clients.

---

## 8. Notification Ownership and Sender

Every notification has a specific recipient.

The `recipient` identifies the user who should receive the notification.

Notification operations are performed in the context of the authenticated user.

A user can retrieve and modify only notifications belonging to that user.

Notifications also store the user who triggered the event through the `sender` field.

For example:

```text
sender    → User A
recipient → User B
type      → message
```

When notifications are retrieved, sender information is populated with the fields required by the frontend:

- `_id`
- `name`
- `profilePic`

Only required sender identity information is exposed through notification responses.

This ownership model prevents users from accessing another user's notification data.

---

## 9. Read State and Unread Count

Each notification contains a boolean `read` field.

The default state is:

```js
read: false
```

A newly created notification is therefore unread.

When an individual notification is read:

```text
read: false
    ↓
read: true
```

The operation is restricted to the authenticated recipient.

All unread notifications belonging to the authenticated user can also be marked as read.

The unread notification count is based on:

```text
recipient = authenticated user
AND
read = false
```

The dedicated unread-count endpoint allows the frontend to display the current number of unread notifications.

Read state is persisted in MongoDB.

The current implementation also synchronizes relevant read-state changes through Socket.IO when connected clients are available.

## 10. Related Entity References

Notifications can reference the application entity associated with the event.

| Notification Type | Related Reference |
|---|---|
| `connection_request` | connection |
| `connection_accepted` | connection |
| `connection_rejected` | connection |
| `message` | conversation, message |

These references allow the notification to remain associated with the context that generated it.

For message notifications, the conversation and message references connect the notification with the corresponding messaging activity.

## 11. Notification API Operations

The Notification Management module exposes authenticated HTTP operations.

**Get Notifications**

```text
GET /api/v1/notifications
```

Purpose:

- Retrieve notifications belonging to the authenticated user.
- Apply pagination.
- Return the newest notifications first.

Supported parameters:

- `page`
- `limit`

Default values:

```text
page  = 1
limit = 20
```

Notifications are ordered using:

```js
createdAt: -1
```

Therefore, the newest notifications are returned first.

**Get Unread Notification Count**

```text
GET /api/v1/notifications/unread-count
```

Purpose:

- Return the authenticated user's unread notification count.
- Support notification badge display.

**Mark One Notification as Read**

```text
PATCH /api/v1/notifications/:notificationId/read
```

Purpose:

- Mark one notification as read.
- Verify notification ownership.
- Synchronize the resulting state with connected clients when applicable.

**Mark All Notifications as Read**

```text
PATCH /api/v1/notifications/read-all
```

Purpose:

- Mark all unread notifications belonging to the authenticated user as read.
- Update the persistent unread state.
- Synchronize relevant state with connected clients when applicable.

The notification API remains the source for retrieving persistent notification history.

## 12. Real-Time Notification Synchronization

The current Nexora implementation uses Socket.IO alongside the persistent notification API.

The two mechanisms have separate responsibilities:

```text
                 Notification System
                         │
              ┌──────────┴──────────┐
              │                     │
              ↓                     ↓
           MongoDB              Socket.IO
              │                     │
              ↓                     ↓
       Persistent State      Connected Clients
```

### 12.1 Persistent State

MongoDB stores the persistent notification information, including:

- Notification record.
- Recipient.
- Sender.
- Notification type.
- Related entity references.
- Read state.
- Creation timestamp.
- Update timestamp.

This allows notification history to remain available after disconnection or reconnection.

### 12.2 Real-Time Synchronization

Socket.IO is used to synchronize relevant notification state with connected clients.

The current messaging and notification integration supports synchronization related to:

- New message activity.
- Unread notification count.
- Notification read state.
- Read state associated with chat activity.
- Conversation-related notification updates.

### 12.3 Notification Read Event

The following Socket.IO event participates in notification read synchronization:

```text
notification-read
```

This allows connected frontend views to reflect notification read-state changes without requiring a complete page refresh.

### 12.4 Relationship with Message Events

The real-time messaging layer also uses message-related events such as:

```text
new-message
message-delivered
message-read
notification-read
```

Message Management remains responsible for message lifecycle behavior.

Notification Management handles the notification state generated by relevant message activity.

### 12.5 Persistence and Real-Time Separation

Socket.IO does not replace MongoDB.

The persistent architecture is:

```text
Business Event
      │
      ├───────────────┐
      ↓               ↓
   MongoDB         Socket.IO
      │               │
      ↓               ↓
Notification      Connected
  History          Clients
```

MongoDB therefore remains the persistent source of notification history, while Socket.IO provides immediate synchronization for connected clients.

Typing, presence, and other transient real-time interaction states are not stored as notification records.

## 13. Database Indexing

The Notification model uses indexes based on the primary notification access patterns.

**Recipient and Creation Time**

```js
{
  recipient: 1,
  createdAt: -1
}
```

This supports retrieving a user's notifications while ordering them from newest to oldest.

**Recipient, Read State, and Creation Time**

```js
{
  recipient: 1,
  read: 1,
  createdAt: -1
}
```

This supports operations involving unread notifications and read-state filtering for a specific recipient.

These indexes are intended to maintain efficient notification queries as notification volume increases.

## 15. Design Principles

The Notification Management module follows these principles:

**Separation of Concerns**

Notification business logic is centralized in the Notification Service.

**Reusability**

Other modules create notifications through `createNotification()` rather than duplicating notification logic.

**Authentication and Authorization**

Users can access and modify only notifications belonging to their authenticated identity.

**Data Integrity**

Notifications maintain references to the users and application entities involved in the event.

**Persistence**

Notification history is stored in MongoDB and does not depend exclusively on real-time delivery.

**Real-Time Synchronization**

Socket.IO synchronizes relevant persistent state with connected frontend clients.

**Scalability**

Pagination and database indexes support increasing notification volume.

**Maintainability**

Notification generation remains integrated with the services responsible for the corresponding business events.

**State Consistency**

MongoDB provides persistent notification state while Socket.IO keeps connected clients synchronized with relevant changes.
