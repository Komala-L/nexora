## 1. Overview

The Nexora Notification Management module provides a centralized system for informing users about important activities occurring within the platform.

Notifications are generated when specific user actions occur, such as:

- A user sends a connection request.
- A connection request is accepted.
- A connection request is rejected.
- A connected user sends a message.

The notification system is integrated with other Nexora modules rather than operating as an isolated feature.

The Connection Management module generates connection-related notifications, while the Message Management module generates message notifications.

---

## 2. Objectives

The Notification Management module is designed to:

- Inform users about relevant activities.
- Maintain a persistent notification history.
- Track whether each notification has been read.
- Provide unread notification counts.
- Allow users to mark individual notifications as read.
- Allow users to mark all notifications as read.
- Associate notifications with the relevant connection, conversation, or message.
- Keep notification creation centralized through a reusable service.

---

## 3. Core Architecture

The Notification Management module follows the Nexora layered backend architecture:

```text
Client
   ↓
Route
   ↓
Authentication Middleware
   ↓
Controller
   ↓
Service
   ↓
Model
   ↓
MongoDB
```

Notification creation follows a slightly different flow because notifications are generated by other business modules:

```text
Connection Service ──┐
                     │
                     ├──> createNotification()
                     │
Message Service ─────┘
                              ↓
                       Notification Service
                              ↓
                       Notification Model
                              ↓
                           MongoDB
```

The Notification Controller handles HTTP-level operations such as retrieving notifications and updating their read state.

The Notification Service contains notification business logic and exposes reusable functionality to other Nexora modules.

Connection Management and Message Management remain responsible for their own business operations. They only invoke the notification creation service when an event requires a notification.

This separation keeps notification responsibilities centralized while allowing other modules to generate notification events without duplicating notification logic.

---

## 4. Notification Types

The system currently supports the following notification types:

| Type | Trigger |
|---|---|
| `connection_request` | A user sends a connection request |
| `connection_accepted` | A connection request is accepted |
| `connection_rejected` | A connection request is rejected |
| `message` | A connected user sends a message |

The notification type is stored as an enumerated value in the Notification model.

## 5. Notification Lifecycle

A notification follows the following general lifecycle:

```text
User Action
    |
    v
Business Service
    |
    v
createNotification()
    |
    v
Notification Document Created
    |
    v
Recipient Retrieves Notification
    |
    v
Notification Displayed
    |
    v
Unread
    |
    +--------------------+
    |                    |
    v                    v
Mark One as Read     Mark All as Read
    |                    |
    +---------+----------+
              |
              v
            Read
```

Notifications are created automatically by the service responsible for the corresponding business action.

## 6. Integration with Connection Management

The Notification Management module is integrated with the Connection Management module.

When a user sends a connection request:

```text
User A
  |
  | sends connection request
  v
Connection Service
  |
  | creates connection
  v
createNotification()
  |
  v
User B receives:
connection_request
```

When a pending connection request is automatically accepted because the recipient sends a reciprocal request, the system creates a `connection_accepted` notification for the original requester.

Connection-related notification creation is handled inside:

```text
src/services/connection.service.js
```

---

## 7. Integration with Message Management

The Notification Management module is also integrated with the Message Management module.

When a connected user sends a message:

```text
User A
  |
  | sends message
  v
Message Service
  |
  +--> Message created
  |
  +--> Conversation updated
  |
  +--> createNotification()
            |
            v
        User B receives:
        message notification
```

The generated notification stores references to:

- The conversation
- The message
- The sender
- The recipient

Message-related notification creation is handled inside:

```text
src/services/message.service.js
```

---

## 8. Notification Ownership

Every notification has a specific recipient.

The `recipient` field identifies the user who should receive the notification.

A notification can only be retrieved through the authenticated user's notification endpoints.

The system does not allow users to access another user's notifications through the notification API.

---

## 9. Sender Information

Notifications also store the user who triggered the event through the `sender` field.

For example, Komala sends a message to Nayana:

```text
sender    -> Komala
recipient -> Nayana
type      -> message
```

When notifications are retrieved, sender information is populated with:

- `_id`
- `name`
- `profilePic`

This allows the frontend to display the notification with the sender's identity and profile picture.

---

## 10. Read State Management

Each notification contains a boolean `read` field.

Default state:

```js
read: false
```

A newly created notification is therefore considered unread.

Users can:

**Mark one notification as read**

The selected notification is updated:

```text
read: false
      |
      v
read: true
```

**Mark all notifications as read**

All unread notifications belonging to the authenticated user are updated to:

```js
read: true
```

The unread notification count is therefore derived from notifications where:

```text
recipient = authenticated user
read = false
```

---

## 11. Notification Retrieval

Notifications are retrieved for the authenticated user using pagination.

The default pagination values are:

```text
page  = 1
limit = 20
```

Notifications are ordered by:

```js
createdAt: -1
```

Therefore, the newest notifications are returned first.

---

## 12. Unread Notification Count

The notification system provides a dedicated unread-count operation.

The count represents the number of notifications belonging to the authenticated user where:

```text
read = false
```

This count can be used by the frontend to display a notification badge in the application interface.

For example:

```text
Bell icon
     |
     v
   [ 3 ]
```

When all notifications are marked as read:

```text
Bell icon
     |
     v
   [ 0 ]
```

---

## 13. Self-Notification Prevention

The notification service prevents a user from receiving a notification generated by their own action.

The service checks:

```text
recipient !== sender
```

If both users are the same, notification creation is rejected.

This prevents invalid notifications such as:

```text
Komala sent you a message.
```

when Komala is also the recipient.

---

## 14. Related Entity References

Notifications may reference the entity responsible for the event.

| Notification Type | Related Reference |
|---|---|
| `connection_request` | connection |
| `connection_accepted` | connection |
| `connection_rejected` | connection |
| `message` | conversation, message |

These references allow the frontend and future features to navigate from a notification to the relevant application context.

---

## 15. Service Responsibility

The Notification Service is responsible for:

* Creating notifications.
* Preventing self-notifications.
* Retrieving user notifications.
* Applying pagination.
* Calculating unread notification counts.
* Marking individual notifications as read.
* Marking all notifications as read.

The service exposes reusable functions for notification operations, including:

* `createNotification()`
* `getUserNotifications()`
* `getUnreadNotificationCount()`
* `markNotificationAsRead()`
* `markAllNotificationsAsRead()`

Business modules call `createNotification()` when a notification-generating event occurs.

The Notification Service also ensures that notification retrieval and modification operations are performed in the context of the authenticated user.


---

## 16. Controller Responsibility

The Notification Controller handles HTTP-level operations for authenticated users.

It is responsible for:

- Receiving requests.
- Passing authenticated user information to the service.
- Returning standardized API responses.
- Handling asynchronous errors through `asyncHandler`.

The controller does not contain notification business logic.

---

## 17. Route Protection

Notification endpoints are protected using the JWT authentication middleware.

The authenticated user is obtained from:

```js
req.user._id
```

This ensures that notification operations are performed in the context of the currently authenticated user.

---

## 18. Database Indexing

The Notification model includes indexes designed around the primary notification access patterns.

### Recipient and Creation Time

The following index supports retrieving a user's notifications ordered by newest first:

```js
{
    recipient: 1,
    createdAt: -1
}
```

This supports the primary notification retrieval pattern:

```text
recipient = authenticated user
sort by createdAt descending
```

### Recipient, Read State, and Creation Time

The following index supports queries that filter notifications by recipient and read state while maintaining creation-time ordering:

```js
{
    recipient: 1,
    read: 1,
    createdAt: -1
}
```

This is useful for operations involving:

* Filtering unread notifications.
* Counting unread notifications.
* Retrieving notifications for a specific read state while maintaining chronological ordering.

The indexes are intended to keep notification queries efficient as the number of stored notifications increases.

---

## 19. Design Principles

The Notification Management module follows the following principles:

**Separation of Concerns**

Notification business logic is isolated inside the Notification Service.

**Reusability**

Other modules can create notifications through:

```js
createNotification()
```

without duplicating notification creation logic.

**Authentication and Authorization**

Notification operations are performed only for authenticated users.

**Data Integrity**

Notifications contain references to the users and entities involved in the event.

**Scalability**

Pagination and database indexes are used to support increasing notification volume.

**Maintainability**

Notification generation is integrated into the services responsible for the corresponding business actions.

---

## 20. Current Scope

The current Notification Management module supports:

- Connection request notifications
- Connection acceptance notifications
- Connection rejection notifications
- Message notifications
- Notification history
- Unread notification count
- Mark one notification as read
- Mark all notifications as read
- Pagination
- Sender information
- Related entity references

Real-time push notifications are not currently part of the module.

Notifications are persisted in MongoDB and retrieved through the notification API.

---

## 21. Out of Scope

The current Notification Management module does not implement:

* WebSocket-based real-time notification delivery.
* Browser push notifications.
* Mobile push notifications.
* Notification deletion.
* Notification preferences.
* Per-type notification settings.
* Notification grouping.
* Notification search.
* Notification prioritization.

These capabilities may be considered in future iterations.

---

## 22. Future Enhancements

Potential future improvements include:

- Real-time notifications using WebSockets or Socket.IO.
- Notification grouping.
- Notification preferences.
- Notification deletion.
- Per-type notification settings.
- Deep linking from notifications to conversations or profiles.
- Browser or mobile push notifications.

These features are outside the current implementation scope.
